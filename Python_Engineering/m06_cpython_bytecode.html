CPython Байткод, Virtual Machine & Evaluation Loop

Подробен анализ на стековата виртуална машина на CPython, структурата на рамките (PyFrameObject), интерпретаторния цикъл в `ceval.c` и адаптивните оптимизации в Python 3.11+.

6.1. Компилационен Пайплайн: Изходен Код до Байткод

Преди CPython да изпълни вашата програма, тя преминава през четири основни етапа на транслация:

  1. Tokenizer: Нарязва чистия текст на лексикални токени (keywords, identifiers, operators).
  2. Parser: Изгражда Concrete Syntax Tree (CST) и го преобразува в Abstract Syntax Tree (AST).
  3. Symbol Table Generation: Анализира областите на видимост (LEGB) и определя типа на всяка променлива (локална, глобална, free/cell).
  4. Code Generation: Превръща AST и Symbol Table в `PyCodeObject`, съдържащ байткод инструкции.

6.2. Стеков Модел и Структура на `PyFrameObject`

CPython е **Stack-based Virtual Machine** (стекова виртуална машина). Всички математически и логически операции се извършват върху заделен за целта стек за оценка (Evaluation Stack).

Всеки път, когато се извика функция, CPython заделя C структура `PyFrameObject` в стека на изпълнение:

cpython/Include/cpython/frameobject.h (C Source)
struct _frame {
    PyObject_HEAD
    struct _frame* f_back;      /* Указател към предишната рамка в извикващия стек */
    PyCodeObject* f_code;       /* Компилираният байткод за тази рамка */
    PyObject* f_builtins;       /* Builtins пространство за бърз достъп */
    PyObject* f_globals;        /* Globals пространство */
    PyObject* f_locals;         /* Locals пространство (dict или бърз масив) */
    PyObject** f_valuestack;    /* Указател към върха на временното стеково пространство */
    int f_lasti;                /* Индекс на последната изпълнена байткод инструкция */
};

6.3. Главният Изпълнителен Цикъл (`ceval.c`)

Ядрото на виртуалната машина е функцията _PyEval_EvalFrameDefault() във файла Python/ceval.c. В нейната основа стои гигантски C switch-case (или Threaded Code скокове през заглавни таблици), който последователно прочита инструкциите от байткода:

ceval.c (Концептуален C модел)
for (;;) {
    opcode = NEXTOP();
    oparg = NEXTARG();

    switch (opcode) {
        case TARGET(LOAD_FAST): {
            PyObject *value = GETLOCAL(oparg);
            PUSH(value);
            DISPATCH();
        }
        case TARGET(BINARY_OP): {
            PyObject *right = POP();
            PyObject *left = POP();
            PyObject *res = PyNumber_Add(left, right);
            PUSH(res);
            DISPATCH();
        }
    }
}

6.4. Дизасемблиране и Анализ с `dis` Модула

Стандартният модул dis позволява декомпилиране на Python код до човешки четими байткод инструкции.

dis_demo.py
import dis

def compute(x: int) -> int:
    y = x * 2
    return y + 5

dis.dis(compute)

6.5. Анатомия на Основните Опкодове (Opcodes)

Опкод Аргумент Действие върху Стека Производителност
LOAD_FAST Индекс в C масив Пушва локална променлива на стека Изключително бързо ($O(1)$ direct array lookup)
LOAD_GLOBAL Име в речник Търси в globals/builtins dict По-бавно (dict hash lookup + fallback)
LOAD_DEREF Индекс в Cell Извлича променлива от Closure Умерено (указател през Cell обект)
STORE_FAST Индекс в C масив Попва стойност от стека и я записва локално Изключително бързо ($O(1)$)

6.6. PEP 659: Specializing Adaptive Interpreter (Python 3.11+)

От Python 3.11 насам CPython включва **Adaptive Inline Caching**. Когато дадена инструкция се изпълни многократно с един и същ тип данни (напр. събиране на две цели числа с BINARY_OP), интерпретаторът динамично мутира байткода на място към специализирана инструкция (напр. BINARY_OP_ADD_INT), заобикаляйки общия C-API диспач.

6.7. Динамична Модификация на `CodeType`

Тъй като PyCodeObject е immutable обект, за динамична промяна на байткод трябва да създадем нов types.CodeType чрез метода replace().

bytecode_mutation.py
import types

def original_fn():
    return "Hello World"

# Извличане на байткода
code_obj = original_fn.__code__

# Замяна на string константата в co_consts
new_consts = tuple("Hacked Bytecode!" if c == "Hello World" else c for c in code_obj.co_consts)
modified_code = code_obj.replace(co_consts=new_consts)

# Замяна на кода на функцията
original_fn.__code__ = modified_code
print(original_fn()) # 'Hacked Bytecode!'

6.8. Практически Казус: Оптимизация на Глобални Търсения (Global Lookups)

Проблема: Вътрешни цикли с интензивни извиквания на глобални функции (напр. math.sin или len) губят време за претърсване на глобалните речници при всяка итерация.

Решение: Присвояване на глобалната функция като локална променлива/подразбиращ се аргумент. Това превръща бавния опкод LOAD_GLOBAL в бърз LOAD_FAST.

lookup_benchmark.py
import math
import time

# Неоптимизиран вариант: LOAD_GLOBAL при всяка итерация
def slow_loop(data):
    res = []
    for x in data:
        res.append(math.sin(x)) # LOAD_GLOBAL math + LOAD_ATTR sin
    return res

# Оптимизиран вариант: LOAD_FAST
def fast_loop(data):
    sin = math.sin # Локално присвояване!
    res = []
    append = res.append
    for x in data:
        append(sin(x)) # LOAD_FAST sin + LOAD_FAST append
    return res

6.9. Практическа Задача и Интерактивен Куиз

Практическа Задача

Използвайте модула dis, за да сравните байткода, генериран от списъчно разширение ([x for x in data]) спрямо традиционен for цикъл с append(). Намерете кои опкодове правят list comprehension по-бързо.

Интерактивен Куиз

Въпрос: Защо опкодът `LOAD_FAST` е значително по-бърз от `LOAD_GLOBAL`?

A) Защото LOAD_FAST чете стойността директно от RAM паметта на видеокартата.
B) Защото LOAD_FAST използва фиксиран индекс в C масив (f_localsplus), докато LOAD_GLOBAL търси ключ в hash речник.
C) Защото LOAD_FAST не поддържа типова проверка.
