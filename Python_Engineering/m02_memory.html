Управление на Паметта, PyMalloc & Garbage Collection

Анатомия на системния алокатор на CPython, разплитане на циклично реферирани обекти, слаби референции и инструменти за откриване на течове на памет.

2.1. Иерархия на Паметта в CPython и PyMalloc

CPython внедрява собствен специализиран алокатор на памет, наречен PyMalloc. Вместо да прави скъпи системни извиквания към OS през стандартния C malloc() за всеки един от хилядите малки обекти, PyMalloc заделя големи блокове памет и ги управлява в потребителското пространство (user-space).

PyMalloc се активира за всички обекти с размер по-малък или равен на 512 байта. Всички по-големи алокации се пренасочват директно към системния malloc() на операционната система.

Ниво в Иерархията Име на Структурата Типичен Размер Отговорност / Управление
Ниво 3 Python Objects Променлив Специфични за типа алокатори (int, list, dict)
Ниво 2 PyMalloc Allocator ≤ 512 bytes Организация в Arenas, Pools и Blocks
Ниво 1 Virtual Memory Allocator 4 KB / Page C Runtime (malloc / mmap / VirtualAlloc)
Ниво 0 Physical Memory (RAM) Хардуер Операционна система (Kernel MMU)

2.2. Архитектура на PyMalloc: Arenas, Pools и Blocks

Паметта под контрола на PyMalloc се организира на три основни структурни нива:

  • Block (Блок): Минималната единица памет с твърд размер (от 8 до 512 байта, кратен на 8). Един блок съдържа точно един PyObject.
  • Pool (Пула): Контигуален блок с размер точно 4 KB (равен на една виртуална страница памет). Всеки Pool съдържа блокове от точно *един* размерен клас (size-class). Половете се поддържат в двойно свързани списъци.
  • Arena (Арена): Голям непрекъснат блок памет с размер 256 KB, заделен директно през malloc(). Една Arena съдържа точно 64 Pool-а и проследява кои от тях са свободни, частично запълнени или пълни.

| ARENA (256 KB)                                                        |
| +-------------------+ +-------------------+     +-------------------+ |
| | POOL 0 (4 KB)     | | POOL 1 (4 KB)     | ... | POOL 63 (4 KB)    | |
| | Size Class: 32 B  | | Size Class: 64 B  |     | Size Class: 512 B | |
| | [Blk][Blk][Blk]   | | [Block][Block]    |     | [ Block ]         | |

2.3. Механика на Reference Counting и C-API Macro Управление

Основният механизъм за управление на жизнения цикъл на обектите в CPython е референтният брояч (ob_refcnt). Всяка променлива, сочеща към даден обект, увеличава този брояч.

refcount_demo.py
import sys

data = [1, 2, 3]
print(sys.getrefcount(data))  # Резултат: 2 (data + аргумента във функцията)

alias = data
print(sys.getrefcount(data))  # Резултат: 3

del alias
print(sys.getrefcount(data))  # Резултат: 2

На ниво C-API управлението се извършва чрез макросите Py_INCREF() и Py_DECREF(). Когато Py_DECREF() заде Same refcount до 0, незабавно се извиква деструкторът tp_dealloc за освобождаване на паметта.

2.4. Поколения на Garbage Collector-а (Generational GC)

Референтният брояч не може да открива и освобождава циклични референции (когато Обект А сочи към Обект Б, а Обект Б сочи обратно към Обект А, без външна променлива да сочи към тях). За тази цел CPython внедрява допълнителен **Generational Cyclic Garbage Collector**.

GC организира обектите в 3 поколения (Generations):

  • Generation 0 (Gen 0): Тук постъпват всички новосъздадени контейнерни обекти. Сканира се най-често.
  • Generation 1 (Gen 1): Обектите, оцелели след сканиране на Gen 0, се повишават в Gen 1.
  • Generation 2 (Gen 2): Дълготрайни обекти, оцелели множество почиствания. Сканира се рядко.
gc_thresholds.py
import gc

# Извличане на праговете за задействане на GC (Thresholds)
print(gc.get_threshold())  # Обикновено (700, 10, 10)

# gc.collect() ръчно стартира пълно почистване на всички поколения
unreachable = gc.collect()
print(f"Освободени недостижими обекти: {unreachable}")

2.5. Алгоритъм за Откриване на Цикли (Tri-color Marking Derivative)

За откриване на затворени референтни цикли GC изпълнява следните стъпки върху контейнерните обекти (листове, речници, персонализирани класове):

  1. Копира референтния брояч на всеки обект в временно поле gc_refs.
  2. Обхожда всички референции вътре в контейнера и за всеки рефериран обект намалява неговия gc_refs с 1.
  3. Всички обекти, чийто gc_refs достигне 0, са потенциално изолирани в цикли и се маркират за унищожаване.

2.6. Слаби Референции (`weakref` Модул)

Слабите референции позволяват достъп до обект без увеличаване на неговия референтен брояч (ob_refcnt). Те са критично важни за кеширащи системи и предотвратяване на референтни цикли.

weakref_example.py
import weakref

class HeavyCacheObject:
    def __init__(self, name):
        self.name = name

obj = HeavyCacheObject("DataPayload")
r = weakref.ref(obj)  # Създаване на слаба референция

print(r() is obj)     # True -> Обектът все още съществува
del obj               # Премахване на единствената силна референция
print(r())            # None -> GC е освободил обекта незабавно!

2.7. Профилиране на Паметта с `tracemalloc`

Стандартната библиотека включва модула tracemalloc, който проследява точната C-линия код, където е била заделена паметта.

tracemalloc_demo.py
import tracemalloc

tracemalloc.start()

# Симулиране на алокация
leaky_list = [dict(a=i) for i in range(10000)]

snapshot = tracemalloc.take_snapshot()
top_stats = snapshot.statistics('lineno')

print("[ Top 3 Memory Allocations ]")
for stat in top_stats[:3]:
    print(stat)

2.8. Практически Казус: Откриване на Memory Leak в Event Pipeline

Проблем: Дълго работеща микроуслуга консумира постоянно нарастващ размер RAM (+500MB за 24 часа). Причината е регистрация на callback функции, сочещи към родителски обекти през closure, създавайки незабележим цикъл.

Решение: Използване на gc.get_objects() и замени на closure референциите с weakref.WeakKeyDictionary.

leak_fix.py
import weakref

class EventDispatcher:
    def __init__(self):
        # Използване на WeakKeyDictionary вместо обикновен dict
        self._listeners = weakref.WeakKeyDictionary()

    def register(self, listener, callback):
        self._listeners[listener] = callback

2.9. Практическа Задача и Интерактивен Куиз

Практическа Задача

Напишете кеширащ декоратор @weak_memoize, който съхранява резултатите от функция, но използва WeakValueDictionary, за да позволи на Garbage Collector-а да изчисти кешираните обекти, когато те вече не се използват никъде в приложението.

Интерактивен Куиз

Въпрос: Какво се случва с обект с размер 128 байта, когато бъде създаден в CPython?

A) Извиква се директно системното извикване malloc() на Linux kernel-а.
B) Заделя се от PyMalloc в съответния Pool с размерен клас (Size Class) за 128 байта вътре в 256KB Arena.
C) Записва се директно в Generation 2 на Garbage Collector-а.
