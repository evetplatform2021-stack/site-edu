11.1. Pytest Архитектура: Fixtures, Scopes & Lifecycle

За разлика от xUnit подхода (setUp/tearDown), pytest използва инжектиране на зависимости чрез **Fixtures**. Fixtures поддържат генератори за точно управление на ресурсите (Teardown phase) и изолационни обхвати (Scopes).

Fixture Scope Жизнен цикъл (Lifecycle) Типично приложение
function (default) Създава се наново за всеки отделен тест. Изолирано състояние, mock обекти, транзакции.
class Създава се веднъж за целия клас с тестове. Конфигурация на тестови клас.
module Създава се веднъж за целия `.py` тестов файл. Тъжки ресурси, файлови симулации.
session Създава се веднъж за цялата тестова сесия. Тестова база данни, Docker контейнери.
test_fixtures_demo.py
import pytest
import sqlite3

@pytest.fixture(scope="module")
def db_connection():
    # Setup Phase
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE users (id INT, name TEXT)")
    yield conn  # Предаване на контрола към теста
    # Teardown Phase
    conn.close()

@pytest.fixture
def db_transaction(db_connection):
    # Използва модулната база, но изолира теста в транзакция
    cursor = db_connection.cursor()
    cursor.execute("SAVEPOINT test_savepoint")
    yield cursor
    cursor.execute("ROLLBACK TO test_savepoint")

def test_user_creation(db_transaction):
    db_transaction.execute("INSERT INTO users VALUES (1, 'Alice')")
    res = db_transaction.execute("SELECT COUNT(*) FROM users").fetchone()
    assert res[0] == 1

11.2. Параметризация & Dynamic Test Generation

Декораторът @pytest.mark.parametrize позволява тестването на десетки гранични случаи с един и същ тестов метод без повторение на код (DRY principle).

test_parametrize.py
import pytest

def is_valid_email(email: str) -> bool:
    return "@" in email and "." in email.split("@")[-1]

@pytest.mark.parametrize("email, expected", [
    ("user@example.com", True),
    ("invalid-email", False),
    ("user@sub.domain.org", True),
    ("user@domain", False),
    ("", False),
])
def test_email_validation(email, expected):
    assert is_valid_email(email) == expected

11.3. Мокинг и Изолация: `unittest.mock` vs `pytest-mock`

Мокингът подменя външните зависимости (API, файлова система, бази данни) с контролирани фалшификати. Златната дума при мокинг е: "Mock where item is USED, not where it is DEFINED".

test_mocking.py
import requests

def fetch_exchange_rate(base: str) -> float:
    response = requests.get(f"https://api.exchangerate.com/{base}")
    return response.json()["rate"]

def test_fetch_exchange_rate(mocker):
    # Подмяна на requests.get с помоща на pytest-mock (mocker)
    mock_get = mocker.patch("requests.get")
    mock_get.return_value.json.return_value = {"rate": 1.95583}

    rate = fetch_exchange_rate("BGN")
    
    assert rate == 1.95583
    mock_get.assert_called_once_with("https://api.exchangerate.com/BGN")

11.4. Property-Based Testing с `hypothesis`

Традиционните тестове тестват конкретни входни данни. hypothesis генерира стотици случайни, но структурирани входове, за да открие непредвидени бъгове и автоматично "свива" (shrinks) открития проблем до най-простия му възможен вариант.

test_hypothesis.py
from hypothesis import given, strategies as st

def encode_decode(text: str) -> str:
    # Симулация на двупосочна функция
    return text

@given(st.text())
def test_encode_decode_property(s):
    # Твърдение: Всеки стринг, преминал през обработката, трябва да е равен на себе си
    assert encode_decode(s) == s

@given(st.lists(st.integers()))
def test_sort_property(l):
    sorted_l = sorted(l)
    assert len(sorted_l) == len(l)
    assert all(sorted_l[i] <= sorted_l[i+1] for i in range(len(sorted_l)-1))

11.5. Мутационен Анализ с `mutmut`

Код покритието (Code Coverage 100%) не гарантира добри тестове. **Mutation Testing** инжектира изкуствени дефекти (мутации) в производствения код (напр. заменя > с >=, или True с False) и проверява дали вашите тестове ще "застрелят" мутанта.

Команда: mutmut run --paths-to-mutate=src/

Ако мутантът оцелее (Survived), това означава, че тестовият ви пакет няма валидация за конкретния логически оператор!

11.6. Модерно Пакетиране: `pyproject.toml`, Poetry, Hatch и `uv`

Инструментът pip и файлът setup.py са наследени системи. Стандартът PEP 621 налага pyproject.toml за единна декларативна конфигурация.

pyproject.toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "my-enterprise-app"
version = "1.0.0"
description = "High-performance Python service"
readme = "README.md"
requires-python = ">=3.11"
dependencies = [
    "pydantic>=2.0",
    "httpx>=0.24",
]

[project.optional-dependencies]
dev = [
    "pytest>=8.0",
    "hypothesis>=6.0",
    "mypy>=1.8",
]

11.7. Production Dockerization & Multi-Stage Builds

Оптимизирането на Docker контейнери изисква минимален размер, липса на C компилатори в продакшън и стартиране от некоренов потребител (Non-root user) за сигурност.

Dockerfile
# Stage 1: Build stage
FROM python:3.12-slim AS builder

WORKDIR /app
RUN apt-get update && apt-get install -y --no-install-recommends build-essential

COPY requirements.txt .
RUN pip install --user --no-cache-dir -r requirements.txt

# Stage 2: Final Runtime
FROM python:3.12-slim AS runner

WORKDIR /app
# Създаване на сигурен non-root потребител
RUN useradd -m -u 1000 appuser

# Копиране само на инсталираните пакети от Builder stage
COPY --from=builder /root/.local /home/appuser/.local
COPY . /app

ENV PATH=/home/appuser/.local/bin:$PATH
USER appuser

EXPOSE 8000
CMD ["python", "main.py"]

11.8. Практически Казус: CI/CD Quality Gates с GitHub Actions

Конфигуриране на конвейер за непрекъсната интеграция (CI), съдържащ проверка на типовете (Mypy), линтинг (Ruff), тестове и качване на метрики за покритие.

.github/workflows/ci.yml
name: Quality Gate CI

on: [push, pull_request]

jobs:
  quality-checks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.12'

      - name: Install uv and dependencies
        run: |
          pip install uv
          uv pip install --system .[dev]

      - name: Run Ruff (Linter & Formatter)
        run: ruff check .

      - name: Run Mypy (Static Type Check)
        run: mypy src/

      - name: Run Pytest with Coverage
        run: pytest --cov=src --cov-fail-under=90

Интерактивен Куиз

Въпрос: Каква е целта на Mutation Testing инструмента `mutmut`?

A) Да генерира автоматично документация за Python API.
B) Да променя производствения код с малки дефекти, за да провери дали вашите тестове са достатъчно качествени и прихващат грешките.
C) Да конвертира Python код към C++ за по-бързо изпълнение.
