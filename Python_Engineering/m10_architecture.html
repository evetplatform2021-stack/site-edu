Софтуерна Архитектура, Дизайн Шаблони и Clean Code

Прилагане на SOLID принципите в динамичен език, патърни за мащабируемост, Dependency Injection, Clean Architecture и поддържане на бизнес логиката независима от рамки и бази данни.

10.1. SOLID Принципи през Призмата на Python

Принцип Идея Имплементация в Python
SRP (Single Responsibility) Един клас трябва да има само една причина за промяна. Разделяне на бази данни/I/O логика от бизнес изчисленията.
OCP (Open/Closed) Отворен за разширение, затворен за модификация. Използване на абстрактни класове, полиморфизъм и декоратори.
LSP (Liskov Substitution) Подкласовете трябва да могат да заменят базовите класове. Спазване на интерфейсните договори без хвърляне на неочаквани грешки.
ISP (Interface Segregation) Малки, специализирани интерфейси пред един гигантски. Множествено наследяване с `typing.Protocol` или леки ABCs.
DIP (Dependency Inversion) Зависимост от абстракции, а не от конкретни реализации. Подаване на обекти през `__init__` вместо вътрешно инстанциране.

10.2. Основни Design Patterns в Python

Python предоставя синтактични улеснения (First-Class Functions, Decorators, Dynamic Typing), които пращат някои класически GOF шаблони в миналото, докато други остават жизнено важни:

strategy_pattern.py
from typing import Callable, Sequence

# В Python Strategy pattern често е просто подаване на функция!
DiscountStrategy = Callable[[float], float]

def regular_discount(price: float) -> float:
    return price * 0.95

def vip_discount(price: float) -> float:
    return price * 0.80

class Order:
    def __init__(self, price: float, discount_strategy: DiscountStrategy = regular_discount):
        self.price = price
        self.discount_strategy = discount_strategy

    def calculate_total(self) -> float:
        return self.discount_strategy(self.price)

order = Order(100.0, discount_strategy=vip_discount)
print(order.calculate_total()) # 80.0

10.3. Dependency Injection (DI) & Inversion of Control

Dependency Injection премахва твърдите връзки между компонентите (hardcoded dependencies), правейки кода лесен за тестване с Mock обекти.

dependency_injection.py
from typing import Protocol

class MessageSender(Protocol):
    def send(self, recipient: str, message: str) -> None: ...

class EmailService:
    def send(self, recipient: str, message: str) -> None:
        print(f"Изпращане на Email до {recipient}: {message}")

class NotificationManager:
    # Зависимостта се инжектира през конструктора (DIP)
    def __init__(self, sender: MessageSender):
        self.sender = sender

    def notify_user(self, user_email: str):
        self.sender.send(user_email, "Добре дошли в системата!")

10.4. Clean Architecture & Layered Design

Основната цел на Clean Architecture е **изолацията на бизнес логиката** (Domain) от външни детайли като frameworks (Django/FastAPI), бази данни (SQLAlchemy) или UI.

  • Entities / Domain: Основни бизнес правила и структури от данни. Не зависят от нищо.
  • Use Cases / Services: Специфична за приложението бизнес логика.
  • Adapters / Repositories: Конвертират данни от базата/API към Domain обекти.
  • Infrastructure: Бази данни, уеб рамки, външни API интеграции.

10.5. Domain-Driven Design (DDD) Основи

DDD поставя акцент върху моделирането на софтуера спрямо реалната бизнес област чрез **Ubiquitous Language** (общ език между инженери и бизнес експерти):

  • Entities: Обекти с уникална идентичност (ID), чиято стойност варира във времето (напр. User, Order).
  • Value Objects: Неизменими обекти (Immutable), дефинирани единствено от техните атрибути (напр. Money(amount=10, currency="EUR")).
  • Aggregates: Група от Entities и Value Objects, третирани като една единица за консистентност на данните.

10.6. Structural Subtyping: `typing.Protocol` срещу `abc.ABC`

Докато abc.ABC изисква номинално наследяване (Nominal Subtyping), typing.Protocol реализира статичен **Duck Typing** (Structural Subtyping) без изрично наследяване.

protocol_vs_abc.py
from typing import Protocol

class Renderable(Protocol):
    def render(self) -> str: ...

# Не наследява Renderable изрично!
class Button:
    def render(self) -> str:
        return ""

def draw_component(c: Renderable):
    print(c.render())

draw_component(Button()) # Валидно за mypy и CPython!

10.7. Data Classes и Неизменими Value Objects

Модулът dataclasses съкращава писането на boilerplate __init__, __repr__ и __eq__ методи. С frozen=True се създават перфектни Value Objects.

value_objects.py
from dataclasses import dataclass

@dataclass(frozen=True)
class Money:
    amount: float
    currency: str

    def add(self, other: 'Money') -> 'Money':
        if self.currency != other.currency:
            raise ValueError("Несъвместими валути!")
        return Money(self.amount + other.amount, self.currency)

m1 = Money(100.0, "EUR")
m2 = Money(50.0, "EUR")
print(m1.add(m2)) # Money(amount=150.0, currency='EUR')
# m1.amount = 200  # FrozenInstanceError!

10.8. Практически Казус: Enterprise Repository Pattern

Изолиране на SQL логиката зад изчистен Repository интерфейс за лесна подмяна на базата данни или тестване с In-Memory речник.

repository_pattern.py
from typing import Protocol, Optional, Dict
from dataclasses import dataclass

@dataclass
class Product:
    id: str
    name: str
    price: float

class ProductRepository(Protocol):
    def get_by_id(self, product_id: str) -> Optional[Product]: ...
    def save(self, product: Product) -> None: ...

# In-Memory Релизация за бързи Unit Тестове
class InMemoryProductRepository:
    def __init__(self):
        self._storage: Dict[str, Product] = {}

    def get_by_id(self, product_id: str) -> Optional[Product]:
        return self._storage.get(product_id)

    def save(self, product: Product) -> None:
        self._storage[product.id] = product

Интерактивен Куиз

Въпрос: Каква е основната разлика между `typing.Protocol` и `abc.ABC` в Python?

A) Protocol работи само по време на изпълнение (runtime), а ABC е за статичен анализ.
B) Protocol използва структурно подтипизиране (duck typing), докато ABC изисква изрично наследяване.
C) ABC не поддържа декоратора @abstractmethod.
